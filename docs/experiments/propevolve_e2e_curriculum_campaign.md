# PropEvolve end-to-end curriculum campaign

## Status

This document defines the implementation contract for a future config-driven
campaign that trains the PropEvolve policy curriculum from scratch. It does not
claim that the current campaign runner already supports the complete multi-stage
flow.

Implementation begins only after the active Stage 2B replay experiment finishes
teacher-free validation. Until then, the current run, checkpoint, configuration,
and evidence remain unchanged.

## Objective

Train one recurrent PropEvolve policy through a bounded curriculum that improves
teacher-free prop-challenge pass rate while preserving zero blows. The long-term
research target is a 60-80% pass rate, but every promotion is incremental and
must beat its immutable parent under the same evaluator.

The first complete campaign is successful when it can:

1. start with no PropEvolve policy checkpoint;
2. train the Expansion Entry foundation;
3. train the Expansion + Regime A+ selector;
4. bootstrap recovery without depending on future recovery artifacts;
5. export exact retained and relapsed recovery examples;
6. refine recovery using those examples and online replay promotion;
7. run greedy teacher-free validation after every learned stage;
8. archive each accepted checkpoint and pass its identity to the next stage;
9. resume only the first incomplete or failed stage after interruption.

## Meaning of from scratch

`from_scratch` means that Stage 1 initializes a new PropEvolve policy. It does
not mean rebuilding authenticated market, FFM, Expansion, Regime, or Entry-label
caches whose complete identities still match the recipe.

The campaign must reuse an existing cache when its source, temporal role,
schema, encoder, teacher, label, and file identities match. It must fail closed
on any mismatch. Rebuilding a valid multi-gigabyte cache is not part of ordinary
policy training.

## Frozen invariants

Every stage preserves these contracts unless a later, separately approved
experiment explicitly replaces one:

- causal completed-bar inputs and next-open execution;
- chronological research, selection, and sealed roles;
- the 2026 sealed period remains untouched until final confirmation;
- one 30-day episode is one prop-challenge attempt;
- +$6,000 pass target and -$3,000 maximum-loss boundary;
- pass, blow, and timeout are the only episode outcomes;
- one-contract position sizing and fee-inclusive execution;
- WAIT, Long, and Short remain learned actions rather than hard teacher gates;
- Expansion, Regime, Entry, and recovery-value outputs are training-only;
- validation and serialized inference perform zero teacher lookups;
- V21 A+ Entry competence must survive Stage 2B recovery training;
- zero teacher-free validation blows is required for promotion;
- a failed child never overwrites an accepted parent.

## Curriculum graph

```text
authenticated immutable inputs
        |
        v
Stage 1 - Expansion Entry foundation (new policy)
        |
        | accepted candidate + teacher-free evaluation
        v
Stage 2A - Expansion + Regime A+ selection (V21 behavior)
        |
        | accepted candidate + healthy-pass replay export
        v
Stage 2B0 - recovery bootstrap
        |
        | completed replay checkpoint
        +----> exact retained-recovery export
        +----> exact retained-versus-relapsed export
        |
        v
Stage 2B1 - recovery refinement with dynamic replay
        |
        | teacher-free matched validation
        v
bounded Stage 2B refinement rounds, if authorized
        |
        v
frozen curriculum candidate
```

The dependency graph is acyclic. Stage 2B0 cannot require a recovery replay
artifact generated by Stage 2B0 or Stage 2B1.

## Autonomous paired-contrastive learning contract

The campaign reuses one recurrent paired-contrastive learning mechanism across
stages. Each stage changes only the economic decision boundary declared by its
recipe:

- Stage 1 contrasts genuine Expansion entries with failed Expansion entries;
- Stage 2A contrasts A+ Expansion + Regime confluence with similar-looking
  failed Long and Short entries;
- Stage 2B contrasts successful recovery with failed recovery, then contrasts
  recovered-and-retained episodes with recovered-and-relapsed episodes;
- later stages may introduce another declared contrast objective only after the
  preceding checkpoint is accepted and frozen.

Every stage records every qualifying success and failure in its evidence
ledger. It extracts only the causal recurrent segments needed for learning into
a bounded, deduplicated replay artifact; it does not serialize an unbounded
full checkpoint for every episode. Long pairs only with Long and Short only with
Short unless a future recipe explicitly defines and validates a direction-
normalized comparison. Matching fields, eligibility, capacity, cadence,
margin, loss weight, and artifact identity are configuration values rather than
stage names or filenames embedded in Python.

The learning boundary is:

```text
good sequence: Q(correct entry side) > Q(WAIT)
bad sequence:  Q(WAIT) > Q(failed entry side)
paired rank:   good advantage > matched bad advantage
```

The replay output of each accepted stage becomes an authenticated input to the
next stage alongside its frozen checkpoint. Later stages retain earlier replay
at the declared sparse cadence so recovery cannot erase Expansion or A+
selection competence.

## Autonomous reasoning-agent contract

The reasoning agent orchestrates and tunes this proven stage graph; it does not
redesign the training pipeline during a run. At a failed stage boundary it may:

- inspect authenticated diagnostics and identify the first failed boundary;
- change only recipe paths explicitly allowlisted for that stage;
- record the rationale and exact before/after JSON diff;
- rerun only the failed stage under a new revision identity;
- select a valid checkpoint and advance when every declared gate passes.

It may not silently change parent checkpoints, data, labels, temporal splits,
challenge economics, outcome definitions, action space, teacher-free inference,
contrast success/failure semantics, sealed evidence, or earlier accepted stage
artifacts. Revisions are bounded by the recipe's attempt budget. Exhausting that
budget ends in `FAILED_GATE` or `BLOCKED`; it never triggers an unbounded search.

The finished operator experience is one validated campaign config and one
launch command. Training, replay export, validation, bounded reasoning
revisions, promotion, checkpoint handoff, and safe resume then proceed without
manual Python edits, hardcoded filenames, or hand-built replay artifacts.

## Stage contracts

### Stage 0 - authenticated preflight

Inputs:

- market-data manifest;
- frozen FFM checkpoint and cache identity;
- Expansion and Regime teacher bundles and caches;
- Entry-label contract and cache;
- chronological split boundaries;
- challenge economics, fees, seed, device, and code identity.

Required result:

- all inputs exist, are finite, causal, and identity-matched;
- the sealed period has not been consumed;
- reusable caches are accepted once rather than regenerated per stage.

Failure status: `BLOCKED`. No training starts.

### Stage 1 - Expansion Entry foundation

Initialization: new recurrent C51 policy with the frozen architecture and seed.

Learning purpose:

- learn WAIT versus Long versus Short around authenticated Expansion
  opportunities;
- preserve asymmetric winners and challenge risk mechanics;
- reach an autonomous, teacher-free tail.

Outputs:

- content-addressed policy candidate;
- teacher-free selection evaluation;
- training diagnostics and replay checkpoint;
- exact recipe, code, cache, seed, and evaluator identities.

Advance only when the declared Stage 1 gate passes. The selected candidate is
immutable after acceptance.

### Stage 2A - Expansion + Regime A+ selector

Parent: accepted Stage 1 candidate.

Learning purpose:

- enter Long for a strong Long Expansion in a ready/non-chop Regime when Short
  evidence does not dominate;
- mirror the behavior for Short;
- WAIT on weak, conflicting, failed-economic, or persistent-chop setups;
- compare exact +2R-before-1R winners with economic failures using recurrent
  Long-versus-WAIT and Short-versus-WAIT learning.

Outputs:

- accepted V21-equivalent candidate and evaluation;
- bounded healthy-pass replay artifact derived from the accepted candidate;
- side, WAIT, chop, opportunity, and paired-economic diagnostics.

The healthy-pass replay is a training aid for Stage 2B. It does not become an
inference input.

### Stage 2B0 - recovery bootstrap

Parent: accepted Stage 2A candidate.

Purpose: produce the first authentic recovery experience without circularly
requiring a prior V22 recovery artifact.

Allowed training inputs:

- the frozen Stage 2A policy;
- recovery start-state curriculum and action-value supervision;
- Stage 2A healthy-pass replay;
- ordinary balanced recurrent replay.

Initially disabled:

- successful-recovery replay whose source would be Stage 2B itself;
- retained-versus-relapsed replay whose source would be Stage 2B itself.

Stage 2B0 must complete its declared training budget even when early recovery
results are poor. Its output is a research checkpoint, not automatically an
accepted Stage 2B candidate.

### Replay export boundary

After Stage 2B0 completes, deterministic exporters read its immutable replay
checkpoint once.

Successful recovery:

- the episode crosses from negative realized PnL to breakeven or better;
- it never returns negative afterward;
- both passes and nonnegative timeouts are eligible.

Relapsed recovery:

- the episode crosses breakeven;
- it returns negative;
- it finishes negative.

Post-recovery contrast pairs:

- pair Long only with Long and Short only with Short;
- match the nearest normalized Expansion + Regime context;
- anchor retained sequences at the first recovery-to-normal boundary;
- anchor failed sequences before the first relapse;
- reject recovered-then-relapsed-then-recovered episodes from both roles;
- require at least one valid retained/relapsed pair before refinement.

Each exported artifact is bounded, content-addressed, atomically written, and
authenticated by the next stage. If exact examples do not exist, the campaign
ends `BLOCKED` with `INSUFFICIENT_RECOVERY_REPLAY`; it does not weaken the
definition or substitute a stale artifact.

### Stage 2B1 - recovery refinement

Parent: the accepted Stage 2A candidate by default. Stage 2B0 supplies replay
evidence, not a replacement policy. This preserves V21 when the bootstrap
policy itself is unsafe or economically weak. A later refinement round may use
the last accepted recovery candidate only after that candidate passes every
promotion and retention gate.

Learning inputs:

- frozen Stage 2A healthy passes;
- exact retained-recovery replay;
- exact retained-versus-relapsed contrast replay;
- current ordinary replay.

During training, newly completed episodes are promoted automatically:

- retained passes and nonnegative timeouts enter successful-recovery replay;
- current retained and relapsed episodes enter the bounded contrast library;
- pairing remains side-specific and nearest-context;
- replay sampling remains at the configured sparse cadence.

The policy continues learning ordinary Entry economics. No V21 action, loss,
handoff, or inference contract is replaced.

### Stage 2B refinement rounds

Further rounds are optional and bounded by configuration. A round may warm-start
from the previous accepted recovery candidate and its authenticated replay
artifacts only when it passes the declared parent-retention gate.

The runner must not loop until a desired result appears. It runs at most
`max_refinement_rounds`, records every result, and stops after the first failed
promotion gate unless a new experiment is explicitly authorized.

## Promotion gates

Every learned stage runs greedy teacher-free validation with epsilon zero.
Training passes do not satisfy a promotion gate.

Stage 2A promotion requires, at minimum:

- zero blows;
- Long and Short participation;
- no universal-WAIT or all-ENTER collapse;
- preserved winner R and Expansion opportunity participation;
- improved or non-regressed pass economics against Stage 1.

Stage 2B promotion requires, at minimum:

- zero blows;
- pass rate strictly better than its matched frozen parent;
- near-blow timeout rate no worse than its parent;
- fewer recovered-then-relapsed failures;
- preserved V21 Long/Short A+ selection and winner competence;
- positive recovery-stress competence;
- zero teacher lookups during validation.

The current 60-80% pass-rate objective is a destination, not permission to tune
on inspected validation. Each accepted child must first demonstrate a real
matched increment.

## Proposed operator interface

The finished implementation should expose one config-selected interface:

```text
python -m propevolve.cli validate-curriculum --config <campaign.json>
python -m propevolve.cli launch-curriculum --config <campaign.json>
python -m propevolve.cli curriculum-status --config <campaign.json> --run-id <run-id>
```

`launch-curriculum` reserves the next versioned run identity and generates the
unattended job definition. Operators do not edit generated job files or Python
configuration constants.

## Runner behavior

The campaign runner must:

1. validate the complete dependency graph before compute;
2. reserve one versioned campaign identity automatically;
3. generate its unattended launch definition from the passed config;
4. execute stages sequentially;
5. persist immutable input and output receipts at every boundary;
6. pass candidate and replay identities through typed stage outputs;
7. never rewrite a stage recipe silently;
8. resume a matching incomplete stage from its checkpoint;
9. skip a completed stage only when its full input and output identities match;
10. invalidate only downstream stages after an upstream identity changes;
11. terminate as `COMPLETE`, `FAILED_GATE`, or `BLOCKED`;
12. keep platform-specific process and log locations outside tracked recipes.

It must not poll, run stages in parallel, inspect the sealed period, retry a
failed hypothesis under the same identity, or rebuild authenticated inputs just
because a new policy stage begins.

## Evidence recorded per stage

- repository commit and dirty-state policy;
- normalized config and config SHA-256;
- parent candidate and evaluation identities;
- data, cache, teacher, label, and replay identities;
- temporal roles and sealed-period status;
- random seed, device, and runtime settings;
- episode and environment-step budgets;
- training pass, blow, timeout, recovery, and replay-promotion diagnostics;
- teacher-free validation and recovery-stress metrics;
- accepted candidate or first failed boundary;
- explicit `PROCEED`, `REVISE`, `STOP`, `INVALID`, or `PROMOTE` verdict.

## Implementation acceptance criteria

Before using the new campaign for expensive training, tests must prove:

1. A fresh-policy smoke run progresses Stage 1 -> Stage 2A -> Stage 2B0 ->
   replay export -> Stage 2B1.
2. Every child receives the exact archived parent selected by the preceding
   stage.
3. Stage 2B0 has no dependency on a future recovery replay artifact.
4. Replay export admits exact retained timeouts and rejects every relapse.
5. Contrast export requires exact finished-negative failures on both sides.
6. Missing matched pairs stop before Stage 2B1 with a typed blocker.
7. A restart resumes the interrupted stage without repeating prior stages.
8. Upstream identity drift invalidates only dependent outputs.
9. Existing V21 and V22 single-recipe campaigns still run unchanged.
10. Final evaluation performs zero teacher lookups and archived policies contain
    no teacher outputs or replay state.

Only after these tests and one bounded end-to-end smoke pass should the runner
be authorized for the full curriculum budget.
